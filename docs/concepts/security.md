# Security model

## What the mirror guarantees

A chart or image a cluster pulls from the platform registry with a valid mirror signature has been through all of this:

1. **Reviewed.** It was merged to `main` through a PR whose diff showed its pin, render and image lock.
2. **Reproducible.** The committed tree regenerated byte-identically from upstream (pr-validate), so the reviewed diff
   is exactly what shipped.
3. **Verified upstream**, where upstream signs. The checks ran in the PR and again on `main` immediately before
   publishing.
4. **Scanned**, with no unaccepted blocking finding and no expired acceptance.
5. **Published by digest** and signed by one workflow identity.

## Keyless signing

The publish workflow signs every chart and image with **its own GitHub Actions OIDC identity**, through Fulcio, with a
public Rekor transparency-log entry. There's no signing key to protect or distribute, and nothing secret on the registry
path. These repositories are public, so the public transparency log is intentional.

```text
issuer:   https://token.actions.githubusercontent.com
subject:  https://github.com/bitwise-media-group/flux-containers/.github/workflows/publish.yaml@refs/heads/main
```

The publish job only runs on `main`, so that subject never varies. A dispatch from any other ref would produce a
different certificate subject, which clusters would reject. Consumers pin that exact identity: the flux-manifests
`OCIRepository` sources, the Kyverno cluster policy, and the `FluxInstance` verify patch. See
[Consuming the mirror](../reference/consuming.md).

patchy also supports a `kms:` signing block (`gcpkms://`, `awskms://`, `azurekms://`), globally or per registry. This
store deliberately uses neither.

## Upstream provenance

Each manifest says how its upstream signs, and the verify stage checks it:

- **cosign keyless**: flux-operator / fluxcd, kyverno (signatures in `ghcr.io/kyverno/signatures`), cilium, dex, the
  OpenTelemetry collector, the actions runner, renovate, and the `registry.k8s.io` images signed by the Kubernetes
  release promoter (external-dns, secrets-store-sync-controller).
- **cosign key**: cert-manager's published project key, with sha512 payload digests.
- **none**: a documented gap. Several upstreams publish unsigned charts (helm `https://` repositories behind
  chart-releaser, and some OCI charts), and a few publish unsigned images (the ARC controller, the AWS Load Balancer
  Controller). These are declared as `provider: none` with a comment, and listed in every verify run, so the gap stays
  visible. For those artifacts, the mirror's signature is the first provenance anything on the path gets.

The [catalogue](../charts/index.md) shows each chart's archive provenance, and each chart page shows the rule every
image matched.

## Publish idempotency

- **An existing chart tag is never replaced.** A version that has been published stays as it was.
- **Images are copied by digest.** Images that are already current and signed are skipped.
- **Upstream mutation fails loudly.** Before publishing, `sync` re-pulls the upstream chart archive and byte-compares it
  with the lock and the committed `vendor/` tree. If upstream changed a released version in place, the publish fails.

## No ungated references

The lint stage checks that the rendered output pulls only from the mirror. Any `oci://` reference to somewhere else must
be listed in the manifest's `ociRefs.allow` with a reason. Today the only one is
[flux-instance](../charts/flux-instance.md)'s default distribution artifact, which consumers neutralise.

## Running PR code safely

pr-validate runs on `pull_request`, where fork PRs get a read-only token. The workflow runs PR code, so
`pull_request_target` isn't an option. The sticky summary comment is posted by a separate workflow, triggered by
`workflow_run` from the default branch. It treats the summary artifact as opaque Markdown and identifies the target PR
from the run's trusted `head_sha`, never from the artifact's contents.
